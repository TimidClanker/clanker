# Context sources v1

Dormant by default: no bindings, listener, observer accounts, classifier processing, imports or provider registrations are enabled by installing this extension. Sources never become authenticated assistant request authors or authorize autonomous work.

## Explicit host setup

`SOURCES_CONFIG` optionally names a JSON array of at most 50 bindings. Each has an opaque `id`, an explicitly permitted `owner` (`{ "identityId": "…" }` or `{ "projectId": "…" }`), and a `principal` label for the connection, not an assistant identity. Provider fields:

- `provider: "github"`, `repositoryId`, `secretEnv`: repository issues and pull-request state events only. HMAC-SHA256 over original bytes, `X-Hub-Signature-256`.
- `provider: "jira"`, exact HTTPS `origin`, `projectId`, `secretEnv`: Jira Cloud **secure-admin**, secret-signed issue-created/updated/deleted events only. HMAC-SHA256, `X-Hub-Signature`. Not Connect/OAuth/JWT hooks, comments or worklogs. Summary/status and string descriptions; no attachment or ADF traversal.
- `provider: "beeper"`, `accountId`, optional nonempty `chatIds`: passive personal account, either explicitly permitted whole account or selected chats. Identity-owned only; distinct from bot account IDs. Uses the existing Beeper transport authentication/client, with no bot-allowlist expansion. No observer queries/subscriptions while all observer sources are inactive (an existing bot socket may already carry envelopes). Both incoming and owner outgoing messages are observed after activation; never passed to assistant admission. No history/attachments.

`secretEnv` is a **host environment-variable name**, never a secret value. The bindings file and secret values are not tool arguments or model context. Use distinct webhook secrets and explicit tenant/resource selections. Bindings are read at host startup; metadata changes require a host restart to take effect. Changing/removing binding metadata then invalidates its source and old disclosure obligations; rotation of the secret value alone need not discard previously authenticated observations.

Optional `SOURCES_PORT` starts Bun's bounded HTTP listener; `SOURCES_HOST` defaults to `127.0.0.1`. Route: `POST /sources/{binding-id}`. Use operator-provided TLS/reverse proxy for external delivery. No webhook registration/subscription API calls are performed. Provider secrets must be configured outside chat. Official signature documentation:

- https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries
- https://developer.atlassian.com/cloud/jira/platform/webhooks/#secure-admin-webhooks

## Verified owner setup

In a genuine verified private owner/project-admin conversation: `list_source_connections`, `create_context_source`, then `configure_context_source` with its current revision. Creation is **inactive**, context on, notifications off. Explicit activation starts a new-message window; it does not import older observations. One source per host binding. No assumed accounts or resources.

`list_source_connections` also lists privately administered source IDs/revisions and whether their binding remains connected. After binding removal/change, the current stored owner/project admin can still delete the old source, but cannot reactivate it or read its observations through that invalid binding.

Personal sources are private to their verified identity. Project-source reads require current project permissions **and** deliberate source audience sharing. Configuring `destination` resolves/verifies that conversation. `shareDestination: true` deliberately adds that destination as a source audience, only if already authorized for the project. `shareDestination: false` with an explicit destination withdraws that source audience, rotates historical authorization, and disables notifications if it was the notification destination. Neither project membership nor a navigation link shares a source. Credentials/principal labels confer no audience permissions.

`SOURCES_CLASSIFIER=provider/model-id` selects a separately configured **bundled native classifier**, not the chat model; split at the first slash. Per-source `externalClassifier: true` is explicit consent to disclose normalized source text to that configured provider/model. Host configuration alone is insufficient. Notifications require that consent and a verified destination. Missing configuration/auth, returned error/aborted results or classification failure leave deterministic context useful and notifications silent; no full-agent fallback.

Importance `threshold` defaults to 0.9 and urgent `highThreshold` to 0.95. These are configurable, **unevaluated starting defaults**, not calibrated accuracy. Important events coalesce for 60 seconds per resource; high-priority ones do not wait for that window. Optional `quiet` has IANA `timeZone`, distinct integer start/end hours (0–23), and explicit `highBypass`; default is no quiet hours. Templates contain a bounded attributed quote, source reference and classification-based reason, with mentions neutralized. Context and notification effects are independent. Both/neither are valid; silent/no useful effect is normal.

`active: false` stops intake/delivery, not authorization to historical excerpts. Ordinary state updates, event expiry and notification/quiet-hour changes do not invalidate conversation history. `withdrawAccess` rotates historical disclosure authorization; deleting a source removes its retained state and withdraws its disclosures. Project/identity/binding revocation is checked independently.

## Bounds, replay and retention

At most 50 sources, 50 latest resources/version watermarks, 50 recent observations, 50 pending observations and 1,000 receipt hashes per source. Normalized text is at most 4 KiB; raw webhook bytes are bounded to 256 KiB and never persisted. Default retention is seven days, configurable 1–30 days. Events retain provider time, receipt time, resource, attribution and reference. Contact claims remain claims, not confirmed facts.

Intake commits observations, dedup receipts and process-task references before ACK/cursor advance. `admitted`, `duplicate`, `excluded` (unsupported/stale/outside the bounded window), and `inactive` are distinct results. Malformed/auth/resource failures reject; pending saturation/durable failure returns retryable 503. Dedup uses authenticated body and semantic hashes independently of unsigned delivery IDs. Equal-time distinct events/resources are not assumed duplicates. Stale updates do not replace newer state. Bounded receipt eviction/expiry advances a timestamp floor; unseen observations at or below that floor are deliberately excluded, even if distinct, rather than claimed as proven duplicates. Equal-time distinct observations above the floor remain admissible. Retained observation IDs also prevent replay. These are best-effort replay/staleness protections, **not** a complete provider ledger/full issue history. GitHub has no signed delivery timestamp: resource-update time plus the activation/window cutoff cannot prove arbitrary replay age.

Source process/notification tasks contain IDs, decisions and checkpoints, not immortal raw-body/SMS copies. Context-disabled processing retains normalized text only while pending. Reads/intake/processing/delivery enforce logical expiry; restore and one-minute housekeeping prune source storage. The source document checkpoints on every change, replacing old current-only document revisions instead of retaining raw deltas. Physical pruning runs only while the host is running or at next restore, not while offline. This is **not** secure disk erasure or deletion from providers/backups.

Beeper retains the original bot checkpoint scope unchanged. Each observer binding has a separate checkpoint, initialized at its activation window and bounded by the current activation cutoff on reconciliation. Changing observer selection cannot reset bot catch-up; failed personal intake cannot advance its observer cursor. Socket and reconciliation transport are shared, not assistant admission.

Notifications recheck access, binding/policy, expiry, newest resource state, quiet hours and already-replied suppression after slow classification and on every chunk/retry. Ordered chat delivery is reused. A provider accepting a send before its durable checkpoint remains an unavoidable duplicate window; accepted chunks cannot be retracted. No exactly-once claim.

## Historical copies and delegated work

A small authorized source directory is in the prompt; history is queried explicitly. Actual excerpts/instructions copied into chat/worker transcripts have that transcript's retention, not fresh source-query lifetime. Current source authorization obligations survive later runs/compaction and follow exact generation/post/media envelopes. Their metadata is rewindable: a fork of pre-reset context inherits its as-of obligations, not cleared or newer authorization. A successfully delivered notification gets a passive `chat.notification` entry whose model role is `user` with an explicit NOT-a-request prefix; immutable evidence is keyed by that entry. It creates no submitted input, authenticated author or agent run, and the assistant consumer ignores it. Notification evidence is included only when its entry is within a future request cutoff; tool/media/job evidence comes from the actual tool-calling generation. Replay of a completed Post creates no second receipt; unsuccessful sends preserve no model quote. Fresh source queries cannot return expired observations. Workers cannot discover/query/admin sources, but genuine user/schedule-approved jobs can use explicitly supplied evidence; start/steer captures immutable evidence obligations. Internal reports cannot add unrelated source evidence or union discovery rights. Normal owner-authorized tools keep their existing permissions.

On actual withdrawal/deletion/binding invalidation only, the next **genuine** assistant-chat input refreshes active model context after old generation/compaction work is terminal. Authorization carry is cleared only in the commit that places a plain Pi reset, with no old-context handoff. A generic notice explains that active context was refreshed and saved chat was not deleted; the new message is processed normally. Reports, schedules and passive source text cannot initiate this recovery. Projects, notes, jobs and stored chat are not deleted. This coarse recovery is a v1 tradeoff, not surgical redaction.

Historical discovery excludes source-bearing model-only/unsent assistant output and internal report inputs; posted excerpts still need their current source obligations. Source-tainted conversation metadata/history can be conservatively unavailable after withdrawal. Query helpers carry the same obligations, including slow/reused queries. Reset never makes private raw/tool evidence into readable chat history. Source retention does not erase chat/worker excerpts, summaries, actually posted notifications, providers or backups.
