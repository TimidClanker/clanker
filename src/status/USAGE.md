# Operational status

`bun run status` prints the running application's local evidence; `bun run status --json` returns JSON. The same source/compiled entrypoint supports `bun run src/index.ts status [--json]` / `./clanker status [--json]`. Dispatch happens before application/auth/provider imports. The current Docker image ships source, so `docker exec <container> bun run status` works without another bot, agent, database reader or public port.

The running app owns a Unix socket at `/tmp/clanker-status-<uid>/status.sock`. Set `CLANKER_STATUS_SOCKET` identically for app and CLI to select another absolute path (at most 85 bytes). Its parent must be an owned, non-symlink directory with mode 0700; socket mode is 0600. Access means local OS-user/operator access, **not** project admin, a conversation role or a model argument. Separate instances need separate paths. Existing sockets/files/symlinks/guards are never replaced at startup. After an unclean process exit, an operator must verify the old process is gone before explicitly removing its stale socket/`.lock` directory; the app never guesses or steals ownership. Bun's automatic socket unlink is confined to the app-created private guard; the published socket is an atomic hard link, removed only if its inode still matches on shutdown.

CLI exit codes: 0 = ready runtime and successful bounded read evidence; 2 = reachable but unavailable/degraded/unknown evidence; 1 = unreachable, invalid/oversized response, timeout or usage error. This is **not** a storage/provider/sandbox health certification. Service reads wait at most 1.5s, CLI requests at most 3s, responses at most 64 KiB. One outstanding collection prevents repeated requests piling up behind a hung read. A permission SDK request without cancellation support can outlive the waiter; no cached authorization is used and subsequent steps check cancellation. Runtime changes during collection discard the old data.

The model-only `get_operational_status` tool calls the same service, never the operator transport. Before returning scoped data it verifies admitted requester provenance, then reuses job/schedule visibility and fresh private-audience/project permission predicates. Permission verification may make narrow platform API reads; status collection itself makes no external health/account/provider/sandbox probes. Read-only destination verification omits the normal subscription side effect. Background-worker tool grants exclude status, explicit requests for it are rejected by the worker-safe tool filter, and the service also rejects delegated workers/report-only runs. Pi's `callers: ['model']` excludes nested tool calls.

## Data and limits

- Build commit (40-hex explicit `CLANKER_BUILD_COMMIT`, otherwise `unknown`), actual Bun version and recorded pinned Pi/AI/Chord/Sandbox package versions. For compilation, supply `--define 'CLANKER_BUILD_COMMIT="<commit>"'`; no runtime Git command or environment dump.
- Process start/uptime; runtime phase/epoch/change time; last 20 in-memory generic runtime-report, ownership-loss, runtime-failure and shutdown-failure event codes/times. Events reset on restart, contain no raw errors and are not complete storage/cleanup history.
- Authorized job ID/title/state/revision/createdAt/updatedAt, waiting-for-coordinator and active workspace-reservation boolean. No workspace paths/IDs, owners, instructions, commands, arguments, progress, questions, results or project identifiers. Model views redact project-task titles rather than grant new project-content disclosure authority. Fresh project authorization still applies.
- Schedule ID/title/state/abort mark, recorded task startedAt/endedAt (nullable), next occurrence/phase, last recurring occurrence time/outcome or terminal outcome **status only**. No destinations/owners/instructions/raw failure text. A sleeping schedule is legitimate waiting, not unhealthy.
- At most 50 newest authorized job candidates and 50 newest global schedule records scanned, filtered to the audience before return; job truncation is explicit. Schedule truncation is `unknown` for model views (no global record-count threshold is disclosed), boolean for the operator. This is not a complete historical search. Use existing list/get tools for more. Shared chats follow existing current-conversation schedule source/destination visibility and requester-owned originating-job rules; linked private chats follow existing canonical-owner rules.

Reads use immutable snapshots, the existing running harness's read-only inspection and its already-open storage's public task scan. No inspection commit, document creation, admission, scheduling, cancellation, retry, repair or lease release. Evidence includes observation/read start/finish timestamps; cached document materialization is not a storage health probe. Failures/timeouts produce no scoped data or raw exception details. Missing history and sandbox availability/cleanup history are explicitly unknown/not recorded. An old job updatedAt is not a heartbeat or proof of being stuck.

This is not a dashboard, full session inspector or tracing system. It does not expose per-answer generation/provider/tool/delivery timing, prompts, reasoning or results, and cannot explain causally why an answer was slow or a briefing did not arrive.
